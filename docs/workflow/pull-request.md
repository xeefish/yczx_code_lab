# Pull Request 评审与合并

完整命令流程见 [`Git 完整上手流程`](../git/quickstart.md)。本文只解释 PR 阶段的协作规则。

## PR 是什么

Pull Request 是将个人分支的变化提交给团队评审，并请求合并到 `main`。它不是上传单个文件，也不是另一种 commit。

一个 PR 应当让评审者快速回答：

- 为什么要改。
- 实际改了什么。
- 怎样确认改动正确。
- 是否存在未解决问题或安全风险。

## 创建前检查

```powershell
git branch --show-current
git status --short --branch
git diff main...HEAD
git log --oneline main..HEAD
```

确认当前不是 `main`，PR 中只有本任务相关文件，且所有 commit 都能解释。

## GitHub 页面设置

- `base`：应合并到的目标分支，通常是 `main`。
- `compare`：自己的任务分支。
- 标题：使用 `docs:`、`feat:`、`test:`、`fix:` 等前缀概括结果。
- 描述：按仓库 PR 模板填写目的、范围、验证和未完成项。

不要勾选或提交与本任务无关的文件。学习记录 PR 通常只包含本人目录下的一份记录；练习 PR 可以包含个人练习目录和相应说明。

## 评审期间

- 评审意见针对代码和文档，不针对个人。
- 不理解意见时先询问，不要猜测后大范围重写。
- 在原分支修改并 `git push`，PR 会自动更新。
- 每个已处理问题在 PR 中回复结果和验证方式。
- 不为同一任务重复创建多个 PR。

## 谁负责合并

仓库维护者在确认范围、安全和验证结果后合并。普通成员不要绕过评审直接推送 `main`，也不要自行使用强制合并或强制推送。

## 合并策略

初期优先使用 Squash and merge，把练习过程中的多个小 commit 收束成一个清楚的 `main` 历史。是否保留完整 commit 历史，由维护者根据任务价值决定。

## 合并后

成员同步本地 `main` 并删除已合并分支。维护者确认任务、会议纪要和周任务中的状态是否需要更新。
