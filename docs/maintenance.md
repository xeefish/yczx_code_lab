# 长期维护与新项目接入

## 维护角色

- 项目负责人：维护平台方向、项目目录和协作边界。
- 文档维护者：检查环境、Git、PR 教程和链接是否仍然可用。
- 项目维护者：维护对应 `projects/<project-id>/` 下的学习路线和任务。
- 成员：发现问题时提交 Issue 或 PR，不只在群里口头反馈。

一个人可以暂时兼任多个角色，但重要权限和知识应逐步有备份理解者。

## 每周维护

每周组会后更新：

- 当前项目任务和完成标准。
- 未解决问题与负责人。
- 可复用示例和常见错误。
- 会议纪要和下一周入口。

每两周检查一次：

- 是否有失效链接或过时命令。
- 成员记录和练习路径是否产生冲突。
- 是否有练习代码应整理为公共示例。
- 是否有内容应该迁移到正式项目仓库。

## 新项目接入步骤

1. 确定项目负责人、正式仓库和项目 ID。
2. 使用 [`项目 README 模板`](./templates/project-readme.md) 创建 `projects/<project-id>/README.md`，说明目标、边界、资料和任务。
3. 在项目 README 中写明负责人、正式仓库、路线、阶段日期、验收标准和产品边界。
4. 按需要创建 `tasks/learning/` 和 `tasks/core/`，先只写未来一至两周。
5. 在 README 中登记学习记录、个人练习、公共示例和正式交付仓库路径。
6. 如果需要新工具，先在 `docs/` 中确认它是否是通用规则。
7. 通过 PR 合并，确认仓库根目录仍然清晰。

新项目不应复制整套环境和 Git 教程。公共基础设施只维护一份，项目差异通过项目 README 和任务说明表达。

## 内容生命周期

- 活跃任务：放在当前项目的 `tasks/`。
- 已完成任务：保留，补充验收结果和会议纪要链接。
- 过时但有参考价值的内容：在文档顶部标记状态，不直接删除。
- 敏感内容、私人资料和临时日志：不进入仓库，必要时在本地或受控系统保存。
